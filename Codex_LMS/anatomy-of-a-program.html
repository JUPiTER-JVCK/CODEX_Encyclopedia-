Systems Compendium · Volume I

Anatomy of
a Program

From bytes on disk to pixels on screen — a complete field guide.

tl;dr
  • A program is a file of machine instructions stored on disk in a filesystem.
  • The OS loader reads it, maps it into RAM, and sets up memory segments.
  • The CPU fetches, decodes, and executes instructions one cycle at a time.
  • The OS mediates every resource: RAM, disk, network, GPU, screen.
  • The GUI is drawn by a render pipeline: layout → paint → composite → display.
  • Every layer below is invisible to the user; every layer above depends on it.
Chapter 01

The File on Disk

Before a program runs it is simply a file — a sequence of bytes stored somewhere in a filesystem tree. On Linux/macOS that tree begins at /; on Windows, at a drive letter. The file is usually an executable binary in a standardized format the OS understands.

FILESYSTEM TREE // where it lives / ← root of everything ├── usr/ │ └── bin/ │ └── firefox ← the executable binary ├── etc/ ← system config ├── home/ │ └── gotti/ │ ├── .config/firefox/ ← user profile data │ └── Downloads/ └── tmp/ ← ephemeral runtime files Permissions: -rwxr-xr-x (owner can read/write/execute) Inode : 2048301 (pointer into filesystem metadata table) Size : 214 MB (stored across many 4 KB disk blocks)
ELF (Linux) Mach-O (macOS) PE/COFF (Windows) Each is a standard container format

Inside the binary container

The executable file is not a plain list of instructions. It is a structured container with a header that tells the OS how to load it.

ELF BINARY LAYOUT // e.g. /usr/bin/firefox on Linux ┌─────────────────────────────────────────────┐ │ ELF Header (64 bytes) │ │ Magic: 7f 45 4c 46 ("ELF") │ │ Architecture: x86-64 │ │ Entry point: 0x004010a0 ← first instr │ │ Program header table offset │ ├─────────────────────────────────────────────┤ │ .text segment ← compiled machine code │ │ .rodata segment ← read-only strings/consts│ │ .data segment ← initialized variables │ │ .bss segment ← zero-init global vars │ │ .plt/.got ← dynamic linking tables │ ├─────────────────────────────────────────────┤ │ Section header table (for debuggers) │ └─────────────────────────────────────────────┘
The magic bytes 7f 45 4c 46 at byte 0 of every ELF file literally spell "ELF" in ASCII. The OS checks this signature before it trusts any other byte in the file.
Chapter 02

Double-Click → The Loader

When you launch a program, the OS does not just "run the file." It goes through a precise sequence: the kernel loader reads the binary, allocates memory, resolves library symbols, then hands control to the program's entry point.

LAUNCH SEQUENCE User Shell / Finder Kernel CPU │ │ │ │ │── double-click ───▶│ │ │ │ │── execve() ─────▶│ │ │ │ reads ELF header │ │ │ maps .text → RAM │ │ │ maps .data → RAM │ │ │ loads shared libs │ │ │ (ld.so / dyld) │ │ │ resolves symbols │ │ │ sets up stack │ │ │ sets up heap │ │ │───── jump to entry_point() ───────▶│ │ │ │ executes!

Virtual Memory — the great illusion

Every process believes it owns the entire address space (e.g., 0x0000 → 0x7fff…ffff on 64-bit). The MMU hardware and OS kernel silently translate these virtual addresses to real physical RAM, page by page.

PROCESS VIRTUAL ADDRESS SPACE // 64-bit Linux 0xFFFFFFFF FFFFFFFF ┌──────────────────────┐ │ kernel space │ ← off-limits to user code 0x0000 7FFF FFFFFFFF ├──────────────────────┤ │ stack │ ← grows ↓ (local vars, call frames) │ ↓ │ │ (unmapped) │ │ ↑ │ │ heap │ ← grows ↑ (malloc / new) ├──────────────────────┤ │ shared libs │ ← libc, libGL, etc. ├──────────────────────┤ │ .bss / .data │ ← globals │ .text │ ← your code 0x0000000000400000 └──────────────────────┘
Chapter 03

The CPU Executes

The CPU runs a tight loop forever: Fetch → Decode → Execute → Writeback. Each instruction is typically 1–15 bytes of machine code that performs one atomic operation.

THE FETCH–DECODE–EXECUTE CYCLE ┌───────────────────────────────────────┐ │ CPU │ │ ┌─────────┐ ┌─────────┐ │ │ │ Fetch │──▶│ Decode │ │ │ └────▲────┘ └────┬────┘ │ │ │ ▼ │ │ ┌────┴──────┐ ┌─────────┐ │ │ │ PC │ │ Execute │ │ │ │(prog ctr) │ └────┬────┘ │ │ └───────────┘ │ │ │ ▼ │ │ ┌──────────────┐ │ │ │ Registers │ ← fast! │ │ │ rax rbx rcx │ │ │ │ rsp rbp rip │ │ │ └──────┬───────┘ │ └──────────────────────┼───────────────────┘ │ (cache miss → RAM) ┌───────────▼───────────────┐ │ L1 cache (4 cycles) │ │ L2 cache (12 cycles) │ │ L3 cache (40 cycles) │ │ RAM (200+ cycles) │ └────────────────────────────┘

Syscalls — asking the kernel for help

User code cannot directly touch hardware. Every time a program reads a file, allocates memory, or draws to the screen, it triggers a syscall — a trap into kernel mode that the OS handles, then returns a result.

PRIVILEGE RINGS ╔═══════════════════════════════════╗ ║ Ring 0 — KERNEL ║ ← direct hardware access ║ ┌───────────────────────────┐ ║ ║ │ Ring 3 — USER │ ║ ← your program lives here ║ │ │ ║ ║ │ open() ─────syscall──▶ ║───╬──▶ kernel handles it ║ │ read() ─────syscall──▶ ║ ║ then returns ║ │ mmap() ─────syscall──▶ ║ ║ ║ │ write() ─────syscall──▶ ║ ║ ║ └───────────────────────────┘ ║ ╚═══════════════════════════════════╝ ~400 syscalls exist on Linux. A typical program uses ~30 of them.
Chapter 04

Shared Libraries & Linking

Programs don't ship every function they use. They link to shared libraries (`.so` / `.dylib` / `.dll`) that are loaded once into RAM and shared across all processes that need them.

DYNAMIC LINKING MAP firefox (process) ├── libxul.so ← gecko engine (90 MB) ├── libc.so.6 ← C standard library (malloc, fopen…) ├── libGL.so ← OpenGL / GPU abstraction ├── libX11.so ← Xorg display protocol (or Wayland) ├── libpthread.so ← POSIX threads └── libssl.so ← TLS/HTTPS All loaded by ld.so (the dynamic linker) at startup. Physical RAM page for libc.so is shared — only ONE copy in RAM even if 50 processes use it. Chapter 05

The GUI Render Pipeline

Once the program logic runs, it needs to put pixels on screen. The modern render pipeline is a layered stack that goes from abstract UI descriptions all the way down to the display controller clocking out voltages to individual pixels.

THE FULL GUI STACK // top → bottom ┌──────────────────────────────────────────────┐ │ Application │ │ "Draw a button at x=100, y=200, w=80, h=30" │ └──────────────────┬───────────────────────────┘ ▼ ┌──────────────────────────────────────────────┐ │ UI Toolkit (Qt / Cocoa / Electron / GTK) │ │ Builds a widget tree, handles events │ └──────────────────┬───────────────────────────┘ ▼ ┌──────────────────────────────────────────────┐ │ Layout Engine │ │ Computes geometry: where does each box go? │ │ Flex, grid, constraints… │ └──────────────────┬───────────────────────────┘ ▼ ┌──────────────────────────────────────────────┐ │ Paint / Rasterize │ │ Converts shapes, text, images to pixel grids │ │ (Skia, Core Graphics, Cairo…) │ └──────────────────┬───────────────────────────┘ ▼ ┌──────────────────────────────────────────────┐ │ Compositor (DWM / Quartz Compositor / Mutter)│ │ Merges all app layers + OS chrome │ │ Uploads final texture to GPU VRAM │ └──────────────────┬───────────────────────────┘ ▼ ┌──────────────────────────────────────────────┐ │ GPU → Display Controller → Monitor │ │ VRAM framebuffer clocked out at 60/120 Hz │ └──────────────────────────────────────────────┘

VSync & the frame budget

At 60 Hz the display refreshes every 16.6 ms. Everything — layout, paint, composite, GPU upload — must finish inside that window or the frame is "dropped" and the user sees a stutter.

FRAME TIMELINE (16.6 ms budget) 0ms 5ms 10ms 15ms 16.6ms │────────────│───────────│───────────│──────│ ├──JS/Logic─────┤Layout───┤Paint────┤GPU──┤ ✓ on time 0ms 5ms 10ms 15ms 16.6ms 20ms │────────────│───────────│───────────│──────│───────│ ├──JS/Logic──────────────────────────────────┤JANK ✗ dropped

The Full Stack, End to End

"The most sophisticated thing your computer does every second is make all of that invisible." — the whole point of an operating system is to be the layer nobody thinks about.
Chapter 07

What a File "Does" When It Loads

Different types of files serve different roles at load time. Here is a quick taxonomy of what each actually does to the process that loads it.

FILE TYPE ROLES AT LOAD TIME Type Loaded by What it contributes ────────────────────────────────────────────────────────── .so / .dll ld.so / LoadLib code + data mapped into proc space .json app runtime config tree parsed into heap structs .png / .jpg image decoder decoded pixel buffer → GPU texture .ttf / .otf font engine glyph outlines → rasterized atlas .glsl / .msl GPU driver compiled to ISA, uploaded to GPU .html / .css browser engine DOM tree + CSSOM → render tree .wasm JS engine near-native bytecode in sandboxed heap .db / .sqlite db engine B-tree pages mmap'd into proc space Every load operation follows the same skeleton: 1. open() the file → get a file descriptor 2. read() or mmap() bytes into address space 3. parse / validate the format 4. build an in-memory data structure the app can use 5. close() the fd → data stays live in RAM
